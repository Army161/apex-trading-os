# ADR 0001: decisions made while building phases 0 to 2

Date: 2026-11-11. Status: in force. These are the places where the build had to choose, or where it departs from `docs/design/`. Each is small. None loosens a safety rule.

| # | Decision | Why |
|---|---|---|
| 1 | Packages export TypeScript source and run with `tsx`. No build step | One toolchain for the CLI, tests and Next.js (`transpilePackages`) |
| 2 | A ledger kind `run` was added | A run with no other effect still needs a record, for the heartbeat and for run-by-run audit |
| 3 | Check 5 doubles both fee and slippage | The design says "2x costs". Doubling only the fee would be the easier reading |
| 4 | Cost priors are slightly above the study's numbers | Costs are judged pessimistically until paper fills are measured |
| 5 | Class exposure cap is `maxClassPct x maxOpen x riskPct x equity` | The design gave a percentage without a base. This reading caps open risk, which is what the rule is for |
| 6 | The file ledger (`.apex/ledger.jsonl`, on the `apex-state` branch in CI) is the ledger of record until `DATABASE_URL` exists | It is durable and append-only, and git history is a second witness. Postgres takes over without a format change |
| 7 | 4h bars use the same epoch-aligned resample as the earlier stress board | Results stay comparable with the 10 Nov board. A session-anchored builder is deferred |
| 8 | A slot whose monthly re-validation no longer reproduces is paused (`paused_data`), not retired | Retirement comes only from the forward record or drift. A data restatement should stop trading, not erase the slot |
| 9 | A paper entry whose open gaps past its stop is cancelled | `backtest()` invents a stop in that case. A system that could go live must never invent one |
| 10 | The validator runs as a separate step before the run, in the same nightly job | A separate workflow needs shared state between jobs. Rule K2 still holds: a pair found tonight is validated tomorrow |
| 11 | Massive's terms are recorded in `data/SOURCES.md` from the approved plan. The build did not re-read them | Accepting terms is Jeremy's. The entry says so |
| 12 | The "diversified core" benchmark is not built. The report says so instead of showing a comparison | It needs the long daily history (Tiingo terms are open) |
| 13 | Refreshed bars extend the committed files in the state directory. The dataset id does not change | Per `04` section 3.3, the same pair on newer bars is the same trial. History is appended to, never refetched |
| 14 | The deflated-Sharpe readout uses every trial ever plus every new pair in the registry | Otherwise the readout depended on the order pairs were evaluated in. It is a readout only and is not part of the result hash |
| 15 | Workflow actions are pinned to major tags (`@v4`), not commit hashes | The build container could not look the hashes up. Pinning by hash is a follow-up |
| 16 | Fingerprint fixtures are frozen copies of three committed data files | Deterministic across machines. They must never be refreshed |
| 17 | The `protected-paths` check stays red on a red-path pull request opened under Jeremy's account, and he merges with the admin bypass | GitHub does not let an author approve their own pull request, and agents open pull requests under his account. A hard lock needs a separate agent account (`docs/branch-protection.md`) |
| 18 | Research-queue tests are ordinary registered strategies with a `queue` tag. They pair only with the `queue-etf-intraday` panel on their own timeframe, are pre-registered as `queue:<id>`, go first in the plan's order, and always wait for the weekly trial budget (25), even in a seeded run | Keeps the queue inside the one factory path, so every queue pair is pre-registered and counted. A queue table in Postgres (design `04` section 16) waits for the database |
| 19 | Rule language version 2 is the same `Spec` with optional parts, and templates are a separate catalog whose defaults must reproduce a built-in fingerprint | Saved version 1 specs keep their exact signals (pinned by a test). Partial exits are left out because the fill engine has no partial fills. A session is clock time and does not know exchange half days |
| 20 | The claim checker (`packages/claims`) is a pure function like the run, and the model's extraction is passed in as data | The command line and the tests never call a model. The app calls it through `web/lib/gateway.ts`. Every quote must occur in the source and every template number must be stated by the source or listed as an assumption, or the extraction is refused. Offsets are repaired by locating the quote, because models count characters badly |
| 21 | Claim-check tries share the weekly budget with the factory and the queue, and a claim that restates a built-in strategy with default parameters uses the built-in's id | Every reading is a real trial and counts toward N. Sharing the id stops the same rules on the same data from being counted, or tried, twice. A check that would go over the weekly budget runs nothing and says so |
| 22 | A stand-in market can at best be a near miss, and `holds_up` also needs a deflated Sharpe probability of 50% or more after deflating by the readings tried in the same check | As designed in 05 s5 and s6. Only an exact ticker counts as the claimed market: SPX, ES or "S&P 500" on SPY is a stand-in |
| 23 | The guard hook's rules live in `tools/guard_hook.mjs` in the repo, and the plugin only holds a launcher that loads them | The rules are reviewed with the code they guard and are a red path themselves. The launcher does nothing outside Apex and refuses the call when the rules cannot load. The hook gets only `APEX_SIGNOFF_KEY` from the environment |
| 24 | The hook refuses `git merge` only on `main`, and `gh pr merge` when the branch touches red paths | The design says to refuse a merge on a branch that touches red paths. Read literally that also blocks merging `main` into a work branch, which is how conflicts are resolved and is harmless |
| 25 | `.env.example` stays a red path, so an agent proposes a new variable in a pull request instead of editing the file | It is in the approved red-path list. The hook's message for other `.env` files says to list the variable there and tell Jeremy |
| 26 | The light-theme live colour is `#ad4e0a`, not the design's `#b4520b` | The design value is 4.49:1 on the chip surface, just under the 4.5:1 rule the same document sets. The contrast test checks every text colour on every surface in both themes |
| 27 | `packages/ui` holds display components only; controls with state (theme switch, filters, dialogs, the claim intake form) come with the app shell and screens | They need the client runtime and the routes they act on, which are P4.2 and P4.3. Everything in the package renders on the server and is tested as static markup |
| 28 | The header's Halt pulls the dashboard's andon cord and also writes a `halt` entry to the ledger | The bots read the cord and the autopilot run reads the ledger, so one press has to reach both. With no ledger connected the header says so and names `apex halt`. Halt needs a signed-in session |
| 29 | Data status in the header has four states: ok, stale, blocked, not checked | A dataset that is only too old to open new paper orders is normal between refreshes and is not a failed health check, so it is shown as stale (warn), not blocked (bad) |
| 30 | The Autopilot and Claim check sections open on a page that says which screens are not built yet | A real route with a plain sentence is better than a missing link. The Autopilot page already shows the funnel from the ledger |
| 31 | Playwright is a pinned dev dependency of `web`, and CI runs `check:ui` against a built app with a fresh paper ledger | The design asks for the browser check on every pull request that touches `web` or `packages/ui`. Market data hosts are ignored in that job, because they refuse some CI networks |
| 32 | The Autopilot screens are server pages over one set of query functions (`web/lib/queries.ts`). Each reads the ledger, replays it with the kernel's own view, and draws from that. No screen keeps its own copy of a number. | A second copy of a figure drifts from the first. The terminal, the report and the screen now come from the same replay. |
| 33 | A halt in the ledger can be released from the Risk screen, by Jeremy only: signed in, same origin, a reason, and the phrase typed out. The route is `web/app/api/resume/`, it is a red path, and it can release `andon`, `kill` and `book-drawdown` and nothing else. | The design asks for a typed confirmation for anything risky (07 s1). Before this the dashboard could halt and only the terminal could resume. It releases a paper halt; it cannot open a live lock, approve or change a limit. |
| 34 | Slot detail has no Pause or Retire button yet, and no equity curve or monkey histogram. | Pause and Retire change a slot's status, which is money code and wants its own reviewed change. The charts need series the ledger does not record yet. |
| 35 | Run reports are drawn by a small parser of our own (`web/lib/markdown.ts`) that turns the text into data, never into HTML. | A report can quote data and error text. Parsed into data, none of it can become markup, and no new dependency is needed. |
| 36 | A claim check in the dashboard is two steps. The plan reads the source, counts the tries and writes nothing, and it carries no result. The run sends the same extraction back, the server checks it against the source again, and the check is recorded | A result that was not counted as a try must never be seen, or the count of tries stops meaning anything. Sending the extraction back avoids a second model call that could read the source differently |
| 37 | The claim screen accepts a saved extraction as JSON in place of the model call | The same door the terminal has. It lets the screen work with no model key, and it is checked against the source like a model's answer: every quote must occur in the text |
| 38 | The result page at `/claims/[id]` is rebuilt from the ledger and has no quotes and no claimed figures | The source text is never stored (05). The full result with quotes is shown once, when the check runs |
| 39 | The dashboard runs a claim check only where it can read `data/` and the engine fixtures from the repo, and it takes the engine fingerprint from the committed `fingerprints.json` | A built server cannot find those files beside its own code. Where they are missing the screen says so and runs nothing. CI already fails when the committed fingerprints and the code disagree |
| 40 | The v1 contract lives in `packages/sdk/src/contract.ts`, and `docs/design/openapi.yaml` is generated from it, not written by hand from `09` | One list feeds the route registry, the OpenAPI file and the client, and a test fails when any of them differs. The design said the YAML is written from `09` and checked against the registry; generating it removes the chance of the two drifting |
| 41 | v1 ships 28 routes. Not built yet: `/strategies`, `/queue/{id}`, `POST /queue`, `/data/datasets/{id}`, `/regime`, `/agents*`, `/automations`, and the public receipts routes | Each needs something that does not exist yet (the research-queue store, the regime panel, the agent roster on the ledger). A route is added to the contract when it can answer truthfully; the scopes `read:agents` and `queue:research` exist and guard nothing yet |
| 42 | `POST /claim-checks` runs the check inside the request and answers `202` with `status: done`. It takes an optional `extraction`, and `GET /claim-checks/{id}` returns what the ledger holds (readings, verdict, flags), not the source's claims | There is no job queue yet, so there is nothing to poll. The source text is never stored, so quoted claims cannot be returned later. `09` section 4 lists `claims[]` and `unsupported[]`; they are in the `202` answer's headline only |
| 43 | API keys live in the dashboard store (Redis), not Postgres, with the last-used time kept beside the list | The dashboard's other settings are there already, and Postgres migrations are a red path with no key table yet. Keeping last-used apart means noting a use can never write over a revoke |
| 44 | A halt through the API is accepted even when no ledger is connected, and counts against its limit before the body is checked | Stopping must never wait on anything. The cord is pulled in the dashboard store either way, and the answer says whether the ledger recorded it |
| 45 | Three model-chat routes that predate the API (`/api/chat`, `/api/risk`, `/api/builder`) still take calls with no session and are held only by the daily AI budget. The inventory test lists them by name | Changing who may use them is a product decision for Jeremy, not part of the API work. They change nothing but their own notes. Recommended: require the session |
| 46 | The ledger queries, the status line and the v1 handlers moved from `web/lib` to a new package, `packages/api`. `web/lib/queries.ts`, `status.ts` and `api/handlers.ts` are one-line re-exports | `08` says a number in the terminal is the same number as on the dashboard. The sure way is one piece of code. The terminal cannot import from `web`, and the handlers already took everything they need as arguments |
| 47 | Every read command asks a `Source` with one method, `call(routeId)`. Local mode runs the handler over this checkout's ledger, remote mode calls the API through the client, and `--fixtures` runs the handler over a committed made-up ledger. `--json` prints that answer unchanged | One renderer and one set of shapes for all three modes. A test checks that remote and local print the same text, and that each `--json` fits the contract's schema |
| 48 | Remote mode is chosen by `--remote`, or by having both `APEX_API_URL` and `APEX_API_KEY` set (`--local` overrides). It refuses a plain `http` address unless it is localhost. `run`, `validate`, `strategies`, `signoff`, `doctor`, `data pull` and `ledger replay` work only in a checkout | `08` section 1. The key must not travel in the clear. Those commands need the code and the data files, which the API does not serve |
| 49 | `apex tui` is drawn with plain terminal escape codes and has no dependency. `08` section 5 names Ink | Ink brings React and about forty packages into the tool that runs the nightly job, for one screen. A pure `frame(data, state, cols, rows)` and a pure `press(state, key)` are easier to test: the tests check every pane at three sizes and try every key. The halt asks for a reason and then the word HALT |
| 50 | Not built in the terminal yet: `regime`, `agents`, `queue add / approve / drop`, `data sources / versions`, `live sign`, and a `--market` or `--tf` choice on `claim` | The API has no route for the first four groups, and approving is Jeremy's on the dashboard. `live sign` belongs with lock 4 (P5). `queue` lists; the rest say where the action is done and exit 2 |
| 51 | `ledger verify`, `ledger replay` and `doctor` exit 4 when the chain is broken (it was 3). A file ledger that fails its own check is refused by the store, and these three report that refusal as the finding. Every other command exits 1 on it | `08` section 2 gives 4 to a failed verification and keeps 3 for "halted or blocked". The nightly job only tests for non-zero |
| 52 | `apex data health` in a checkout checks the data files themselves, as before. With `--remote` or `--fixtures` it shows what the last run recorded | In a checkout the fresh check is the useful one and CI relies on it. Away from one, the files are not there |
| 53 | The MCP server uses the official TypeScript SDK (`@modelcontextprotocol/sdk`, MIT, pinned to 1.32.2) through its low-level `Server`, not the `McpServer` helper | The helper wants zod schemas. The low-level class takes JSON Schema, so each tool's output schema is the contract's own and cannot drift. Input is checked with the contract's validator. The official client is used in the tests, in memory, over stdio and over HTTP |
| 54 | Over HTTP the MCP route is stateless (one POST, one JSON answer, no session, no stream) and makes every tool call through the v1 client into `serve`, in process, with the caller's own key | A tool call is then an API call: scopes, rate limits, the halt and the budget apply with no second copy of the rules. Stateless suits serverless and leaves no session to steal. OAuth comes with the product (`12`) |
| 55 | Thirteen tools, not the fifteen in `10` section 1.1: `apex_strategies` and `propose_research` are not built | The v1 contract has no route for the strategy registry or for proposing research, and the server adds nothing the API lacks. Both wait for those routes (P4.11) |
| 56 | Every tool's text is wrapped in one marked block (`<apex-data>`), not only the tools that carry outside text. `apex://playbook` and `apex://design/README` exist only on the stdio server | Halt reasons, ledger payloads and hypotheses can all hold outside words, so one rule for all is simpler to hold than a list. The hosted route has no repo files to read |
| 57 | In local mode `apex mcp` can read and halt but not start a claim check. The old Python server keeps `list_strategies`, `scan` and `dashboard_status`; `backtest` and `leaderboard` are removed | The extraction needs the model, and only the dashboard's gateway may call one. The two Python tools ran tests that nothing counted (`10` section 1.3) |
| 58 | `tools/list` is about 40 KB because each tool carries its output schema | `10` asks for input and output schemas, and the client checks answers against them. If a Claude client turns out to load output schemas into the conversation, drop them: the data does not change |

## Open question for Jeremy

With one slot, the weight cap is 25% of equity and there is no leverage. On `dave_prev_range` SPY 1h the stops are tight, so the cap leaves less than half of the intended risk on 68 of 79 past signals. The guard blocks those (`minRiskShareAfterCap` is 0.5). Graduation is not affected, because the slot's own record is kept at fixed risk. The paper book would take few of its trades. The safe alternative is to take the smaller capped size instead of blocking. That changes a gate setting, so it makes a new gate version, and it is Jeremy's call.
